# PDD 数据同步设计

## 状态

当前同步层状态：`adapted`。

这表示代码已经适配以下接口名称和常见响应结构，但尚未使用本项目真实授权店铺逐项验证全部字段：

- `pdd.goods.list.get`
- `pdd.goods.detail.get`
- `pdd.order.list.get`
- `pdd.order.number.list.increment.get`
- `pdd.order.information.get`
- `pdd.refund.list.increment.get`
- `pdd.refund.information.get`

真实可用性仍取决于应用类型、审核状态、店铺授权 scope 和拼多多当前安全要求。

## 同步策略

### 商品 / SKU

首次同步分页读取店铺商品列表，再读取商品详情，将商品和 SKU 标准化写入 SQLite。商品同步完成后会尝试把过去未能匹配 SKU 的订单明细和售后记录重新关联到新同步的 SKU，并刷新每个 SKU 最新一条指标中的价格与库存。

### 订单

首次同步使用历史订单列表按天分窗读取，默认回溯 30 天，允许 1~90 天。日常同步使用订单增量接口，按 30 分钟时间窗拆分，再按订单号读取详情。

订单更新时只有在新的详情确实包含商品明细列表时才替换本地 `order_items`。如果平台返回的是不完整详情，不会先删除已有明细，避免一次不完整响应把已经同步的数据降级。

### 售后

使用售后增量接口按 30 分钟时间窗拆分；如可用则继续读取售后详情。更新记录时会同时把旧日期和新日期加入重算范围，避免时间字段变化后旧日期仍残留退款数据。

### SKU 指标

订单和售后写入后，只重算受影响日期的成交/退款指标。重算前先把这些日期现有 `order_count / sales_qty / gmv / refund_count / refund_amount` 清零，再根据本地订单和售后重新聚合，因此订单更新、日期变化或关联变化不会留下历史脏值。

曝光、点击、访客、推广等由报表导入的字段不会被成交重算覆盖。

## 失败恢复与幂等

同步任务写入 `sync_jobs`，状态包括 `queued`、`running`、`success`、`failed`。任务同时保存原始同步参数，因此失败后可以从 UI 直接“按原参数重试”。

应用启动时会扫描仍停留在 `queued/running` 的任务。这通常意味着用户在同步过程中关闭程序或程序异常退出。这类任务会自动标记为 `failed + recoverable`，从而不会永久阻塞该店铺的新同步任务。

商品、订单、售后均使用平台 ID 做本地 upsert；同步游标只在对应资源完整执行成功后推进。任务中途失败时不会推进游标，因此重试会从上一次已完成位置重新读取，依赖幂等写入消除重复。

## 请求级重试

PDD Client 对以下临时性失败进行有限次数重试：

- HTTP 429；
- HTTP 5xx；
- 网络传输异常；
- 返回文案明确表示系统繁忙、频率过高、稍后重试等临时错误。

权限不足、参数错误等确定性错误不会自动重试，避免无意义地重复调用。

## 自动诊断

完整同步、订单同步、售后同步或日常增量同步如果确实产生了经营数据变化，会自动重新运行店铺 SKU 的确定性诊断。相同 `SKU + period_end` 的诊断记录采用更新语义，不重复无限新增；若确定性诊断内容发生变化，旧 AI 分析会被清空，避免展示基于旧证据生成的建议。

## 本地任务与自动同步

不引入 Redis/Celery。桌面进程内使用线程池执行同步任务，守护线程定期扫描自动同步配置；到期后提交增量任务。最低自动同步间隔为 15 分钟。

同步游标存入 `sync_cursors`，自动同步配置存入 `sync_preferences`。

## UI 状态

页面顶部持续显示当前店铺同步状态。数据中心展示当前任务、进度、最近任务历史和错误原因。失败或中断任务提供直接重试按钮。后台同步完成后会触发前端数据更新事件，在用户停留于 Dashboard 或 SKU 诊断页时自动刷新当前视图。

## 安全

同步逻辑只从本地加密存储中解密 Client Secret / Access Token。订单原始 JSON 只保存在本机，不会自动发送给 AI Provider。

如果未来接入收件人解密等敏感接口，必须另行满足拼多多平台的云内/安全要求，并单独做隐私审计。
